# citygov — Kanton Schaffhausen compliance databank

Machine-readable databank that, per **city service**, captures the **laws** that
govern it (down to the article), the **requirements** those articles impose, the
**forms** that collect the data, and the **reconciliation** between law and form.
The consumer is an LLM agent that will administer services — so the data must be
**precise, auditable, and never silently wrong**. Surfacing gaps and
over-collection honestly is the whole point; a fake "100 % compliant" is a defect.

## The three reconciliation buckets (the deliverable)
- **Match** — law demands it, a form field collects it (CONFIRMED). Compliant.
- **Legal gap** — law demands it, no form field captures it. Form non-compliant.
- **Over-collection** — form collects it, no legal basis. Potential DSG issue.

A requirement matched only by a *proposed* (auto, unconfirmed) mapping is **not**
counted as compliant — it is reported separately. Compliance % = confirmed
matches / total requirements.

## Non-negotiable conventions (from real prior failures — do not relax)
1. **Form content beats form title.** Decide which service a form serves by
   reading its actual fields/checkboxes/attachments, not its title. Record any
   title↔content mismatch on `form.title_content_mismatch` + `mismatch_note`.
2. **Split nominal services** when a form's demanded data set is largely disjoint
   from another nominally-same service. `service` is the modelled unit.
3. **Form-side and law-side are independent.** `form_field` has NO FK to
   `requirement`. The only link is `field_mapping`. This is what makes
   over-collection structurally representable.
4. **Five field classifications, never collapsed** (`field_mapping.classification`):
   `mapped`, `identity_part`, `reason_facet`, `form_mechanic`, `overcollection`.
   Over-collection is only meaningful after the other four are removed from
   contention. Name/Vorname/Geburtsdatum are `identity_part` of one Personalien
   requirement — NOT three over-collections. Each checkbox of a Gesuchsgrund is a
   `reason_facet` — NOT over-collection.
5. **Auto-match proposes, never confirms.** Everything `propose_mapping.py` emits
   is `match_status='proposed', mapped_by='auto'`. A human flips real ones to
   `confirmed`. The dashboard shows the difference.
6. **Never type a citation from memory.** Real Art./§/Abs. come from the actual
   law text. Cantonal laws are in `../Gesetze/` (official SHR PDFs) — read them
   offline with `scripts/extract_law.py` (macOS PDFKit via JXA; no deps, no
   network) and record the article WITH its provenance. Three verification levels
   live in `last_checked`:
     * `verified`                      — cross-checked live against Fedlex/register
     * `Gesetze-PDF <SHR> (Stand …)`   — read from the official cantonal PDF (amber "Quelle" badge)
     * `UNVERIFIED`                    — no source yet; unknown article = `article_no='UNKNOWN'`
   Federal (Fedlex) and communal texts are NOT in `../Gesetze/`; record only what
   an authoritative source states (e.g. a federal article *cross-referenced by* a
   cantonal law), leave the SR number `UNVERIFIED` until a real source is given —
   do not guess it. `logs/citation_todo.txt` is the verify list. `§` uses §, not Art.
7. **Classify before modelling** (`classify.py`): `formular` (enters pipeline) vs
   `calculation_tool` (Excel formula — document `formula_note`, do NOT model as a
   form) vs `helper` (Wegleitung/Merkblatt — catalogue only).
8. **Dedupe requirements by data point** (`requirement.data_point_key` is UNIQUE).
   Before creating a requirement, the committer reuses an existing one with the
   same key (e.g. one shared `personalien`). Legal bases are M2M
   (`requirement_legal_basis`), so a shared requirement can cite several laws.
9. **One source of truth = `citygov.db`.** `data_export.json` and `dashboard.html`
   are GENERATED by scripts and must never be hand-edited.
10. **Idempotent, validated, copy-then-swap writes.** `commit_proposal.py` works on
   `citygov.db.staging`, upserts (check-before-insert, re-runnable), validates
   (no orphan FKs, no duplicate join rows, classification coherence,
   document↔form linkage), and only then atomically swaps. On any failure it
   aborts and leaves the DB untouched. (A duplicate-row bug once inflated scores.)

## Schema (see `schema.sql`)
`service` · `law` · `article` · `requirement` · `requirement_legal_basis` (M2M
requirement↔article) · `service_requirement` (M2M) · `form` · `form_field`
(law-blind) · `field_mapping` (one row/field: classification + nullable
requirement_id + match_status) · `process_step` (automatable|manual) · `document`
(inventory, conv 7) · `finding` (declared flags; gaps/over-collection/citation
TODOs are *derived* at export, not stored).

## Pipeline / operating loop (adding a service or form)
```
# 0. one-time
python3 scripts/init_db.py                      # create citygov.db from schema.sql

# 1. classify the source files (conv 7)
python3 scripts/classify.py forms/              # -> inventory/<dir>.classified.json  (REVIEW)

# 2. extract a Formular's actual fields, law-blind (conv 3)
python3 scripts/extract_form.py forms/X.pdf     # -> proposals/<slug>.extracted.json
#    (pip install pypdf openpyxl  for real PDF/Excel extraction)

# 3. model the LAW side by hand in the proposal: read the form CONTENT (conv 1),
#    decide the real service (split if needed, conv 2). Find the governing law in
#    ../Gesetze/ and read the REAL article/§:
python3 scripts/extract_law.py ../Gesetze/120.100-3-1.de-1.pdf --grep Meldepflicht
python3 scripts/extract_law.py ../Gesetze/120.100-3-1.de-1.pdf --index
#    Add laws/articles with real Art./§ + provenance last_checked (conv 6),
#    requirements (reuse data_point_key, conv 8), service_requirements.
#    (mdfind -onlyin ../Gesetze "<Begriff>" helps locate the right SHR PDF.)

# 4. auto-propose mappings (conv 5)
python3 scripts/propose_mapping.py proposals/<slug>.extracted.json
#    -> proposals/<slug>.mapped.json ; REVIEW, flip real matches to confirmed.

# 5. commit into the source of truth (conv 10 safety wrapper)
python3 scripts/commit_proposal.py proposals/<slug>.json

# 6. regenerate the dashboard
./build.sh                                      # export_json.py + build_dashboard.py
open dashboard.html
```
The worked example `proposals/anmeldung-wohnsitz.json` is a hand-authored instance
of the proposal format (steps 2–4 already done) and seeds the databank.

### Bulk auto-draft (first-draft, review required)
`scripts/auto_draft.py "<office-dir>"` (or `--all`) processes every Formular:
copies it into forms/, extracts real fields (AcroForm → flat-PDF text incl. Word
'Label/[placeholder]' style → Word .doc/.docx via macOS `textutil`), and loads a
DRAFT service with **one requirement per field** (the data point), each
`legal_basis=[]` → "Rechtsgrundlage zu ermitteln". It does NOT assign a per-field
basis: the correct basis is service-specific (a "Name" field on a weapons permit
vs tax return vs registration differ), so guessing violates conv 6 — the forms'
cited laws are recorded as research leads in the draft finding. Every mapping is
`proposed`/`auto` — nothing reads as compliant. The whole Verwaltung collection
(211 services / 8326 fields / 6588 per-field requirements) was drafted this way and
must be REVIEWED. Draft limits, by design: (a) 11 scanned image PDFs need OCR (no
tesseract here; macOS Vision via JXA or a brew install) + 8 prose declarations
have no fillable fields; (b) per-field legal basis is the review work; (c) legal
GAPS aren't detected (draft is field-derived); (d) over-collection is a review
finding (a field whose basis search comes up empty).

Review loop per service: open it in the dashboard → confirm the real service &
title-vs-content (conv 1) → for each field find the governing law's real Art./§
(extract_law.py for cantonal Gesetze / Fedlex for federal) and fill its
legal_basis → flip true matches to `confirmed`; a field with no basis becomes
`overcollection` → re-run `./build.sh`.

## Dashboard (`dashboard.html`, generated)
Self-contained (JSON inlined, opens via `file://`, no server, offline). Left
service filter + three views: **Abgleich** (reconciliation, 3 colour-coded buckets
+ compliance summary), **Gesetzes-Baum** (Gesetz→Artikel→Anforderung as both a
collapsible list tree and a collapsible node diagram), **Geforderte Informationen**
(per-law required-data table). Colour encodes jurisdiction / match status /
classification. UNVERIFIED citations are badged.

## Git
Every meaningful change is a commit. Never amend or rebase — history is the audit
trail. `citygov.db`, `data_export.json`, `dashboard.html` are committed (generated,
but kept so the example is openable from the repo); regenerate them, never edit.
