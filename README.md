# citygov — Compliance-Databank Kanton Schaffhausen

> **▶ Open the dashboard: <https://jastephan63.github.io/citygov/dashboard.html>**
> — nothing to install, runs in any current browser (Chrome, Edge, Firefox, Safari).
> Start page with the dossiers and the guided forms: <https://jastephan63.github.io/citygov/>

A database of the canton's administrative services. For each service it
records: the laws behind it (down to the article), the data its Formulare
collect (down to the single field), the standard each datum maps to (eCH, or
the draft cantonal standard eSH), the rules for handling that data (storage,
retention, disclosure), and how far the service is from being fully digital.

Gaps are shown as gaps. If a legal basis is missing or unverified, the
dashboard says so instead of hiding it.

It is written for two readers: peer administrations building the same kind
of databank, and an LLM agent that has to process cantonal services from it
— which is why every statement has to be precise, sourced and never silently
wrong.

## Opening the dashboard

**In the browser — the easy way.** Open
<https://jastephan63.github.io/citygov/> (start page) or go straight to
<https://jastephan63.github.io/citygov/dashboard.html>. The site is this
repository served by GitHub Pages, so it always shows the latest pushed
version, and the links to the dossiers and to the original Formular files
work there too. The dashboard is one page with all data built in: about
4 MB travel over the network, and the browser then needs a few seconds to
read the data — the page says so while it loads.

**Not on github.com itself.** GitHub cannot display a file this large, and
its «Raw» button shows the file as plain text (source code) instead of the
dashboard. Use the link above instead.

**An offline copy of the dashboard alone.** On the start page, right-click
«Dashboard öffnen» and choose «Save link as…» (or «Download linked file»),
then double-click the saved `dashboard.html` (Mac: Ctrl-click the link; in
Safari the menu item is «Download Linked File»). It runs without internet in
any current browser. In such a single copy the links to dossiers, Formular
files and guided forms open on the website; fully offline they need the whole
repository (next option).

**Everything, offline.** Click the green **Code** button at the top of this
page and choose **Download ZIP**: about 170 MB to download, about 340 MB
unpacked — about 150 MB of that is the original Formular files in `formulare/`.
Unzip it and double-click `index.html` (start page) or `dashboard.html`; everything, including the dossiers and the original Formular files, then works without internet.
Or clone it (about 230 MB to transfer, growing with every update, since the
history keeps each version; `git pull` brings updates later):
```bash
git clone https://github.com/jastephan63/citygov.git
```

**If a browser is slow with the file.** Some browsers handle a page this
size better over http than from a double-clicked file. In the folder, run
```bash
python3 -m http.server 8917
```
and open `http://localhost:8917/`. Any other static file server works too.

`datentresor.db` opens with any SQLite client, for example
`sqlite3 datentresor.db` or DB Browser for SQLite.

## How the dashboard is organised

- **The data standard comes first.** The start page opens with three figures:
  how many data points carry an eCH element, how many are demanded the same
  way as on the other forms, and how many fields still carry a deviating name.
  Legal-basis and register gaps follow, then the open points.
- **Three entry points**, one per reader: *Für Dienststellen* (what an office
  has to change on its forms — one page per Dienststelle with its most
  important actions, printable as a brief), *Für den Kanton* (what has to be
  decided) and *Methode & Quellen* (how the databank is built).
- **The colour says who acts next**, on every page: green settled, red the
  Dienststelle changes its form, amber the canton decides, grey the databank
  still has to research it. Open points are gaps, not findings of a breach.
  The Gestaltung page keeps these colours and says in its own words what
  they mark there (see below).
- **Priorities**: data standard, then legal basis, then procedure & register,
  then inventory & currency. The databank's own research homework has its own
  page («Recherche der Databank») and is kept off the offices' lists.
- **Gestaltung der Formulare — a part of its own.** How the Formulare look
  and are presented, compared with each other: Schrift, Farben, the
  Mindestmerkmale of accessibility, Kontaktangaben and Aufbau. It has its
  own sidebar group «Erscheinungsbild», right after the data standard, and
  opens like the start page: the question «Wo anfangen?» with seven doors —
  first the readers, *Je Dienststelle* and *Für den Kanton* (the Merkmale
  without a clear practice or rule), then the five groups. Per Merkmal the
  page shows the practice (or «keine klare Praxis»), the measured values as
  a neutral list, the findings in their colour and, folded, the Formulare
  concerned, each linked to its Formular view; the table *Je Dienststelle*
  keeps the order of «Für Dienststellen» (by Departement, A–Z) and counts
  Abweichungen and Lücken apart. Every section has a shareable address (e.g.
  `#gestaltung/all/barrierefrei`). Every Formular has a folded panel
  «Gestaltung» on its service page and in its Formular view, every
  Dienststelle brief a short section «Gestaltung ihrer Formulare»; the start
  page has one link line under its doors, and «Für den Kanton» one pointer
  to the Merkmale without a clear practice. In this part green is
  «entspricht der Praxis» or «vorhanden», red «weicht ab» or «Lücke» (a
  difference on the Dienststelle's Formular, no request to change it —
  whether a rule is broken, the databank cannot say), amber «keine klare
  Praxis» (no rule lies before the databank; the canton decides, once per
  Merkmal) and grey «nicht messbar» or «noch nicht gemessen» (open with the
  databank, no finding about the Formular); the measured values themselves
  carry no colour, and numbers are written with a decimal point like
  everywhere else. The texts describe what differs and never ask an office
  to change its Formular. The
  figures stay on this page: they are not part of the headline figures, the
  open points, the Handlungsbedarf or the priority tiers.
- **Trend**: every figure is compared with the previous snapshot in
  `verlauf.json`; notes explain jumps. Shares are shown with one decimal
  everywhere (68.5 %), so a small movement between two builds stays visible.
- **Terms and contacts.** A glossary on «Methode & Quellen» explains the
  databank's terms (Datenpunkt, eCH-Element, Teilfeld, Divergenz …); the
  headline cards explain the same terms on a tap. A Dienststelle's contact is
  written the same way on every page, in the dossiers and in the guided
  forms: «Kontakt (laut DVSH): Adresse · Tel. … · E-Mail …», the stored
  values verbatim, telephone and e-mail as links.
- **One look.** Fonts, colours, the four tones and the six text sizes are
  defined once (`scripts/theme.py`) and used by the dashboard, the start page,
  the dossiers and the guided forms; every text colour reaches a contrast of
  4.5:1 and no text is smaller than 12 px — the page check at the end of the
  build measures both.
- **Prototypes** (the synthetic Datentresor view, the guided forms) sit in a
  separate «Werkstatt» section; the eSH standard is marked as a draft wherever
  it appears.
- **Wording.** German readers take «Datum» as a calendar date, so the
  databank's own German texts say «Datum» only for dates, «Angabe» for a
  single piece of information and «Daten» for data in general. Quotes from
  forms, laws, eCH, DVSH and SHEP stay verbatim. The reviewed rewrites of the
  databank's texts are kept in `quellen/wortwahl_datum.json` and applied by
  `scripts/apply_wortwahl.py`; the build stops on a new naming or basis text
  that says «Datum» without a verdict there.

## What the data covers

- **Services and Formulare.** The unit is the service as modelled in the
  canton's service model (DVSH); Formulare belong to services, and a service
  can have several. Since 2026-09-27 every DVSH service whose model declares
  its own file or procedure has its own row (the evidence per row is in
  `quellen/korrekturen/dvsh_aufteilung_2026-09-27.json`); 5 rows carry several
  DVSH services that all name the same file, under a name taken from DVSH
  wording. Of the 491 services, 324 are linked to their DVSH entry, 7 are
  modelled in DVSH but missing from the current harvest (shown as
  «DVSH-Modellierung nicht in der Databank»), and 160 are services the DVSH
  model does not contain yet — kept as they are, never force-fitted. 75
  services have no Formular: 72 DVSH services, most of them reached through
  an eFormular without field definitions, by e-mail, phone, an external link
  or in person, and 3 of the 7 whose DVSH entry is missing. One of the 72,
  service 640 (DVSH 206, split off on 2026-09-27), does have a DVSH
  eFormular definition with 15 fields that has not been loaded yet (see
  «Known gaps»).
- **Data fields.** Each Formular's fields, broken down to atomic parts
  (Name, Vorname and Geburtsdatum separately, not just "Personalien").
- **Standards.** The eCH catalogue (290 standards, about 9,700 elements)
  plus eSH, a draft cantonal standard for everything eCH does not cover.
  eSH is always marked as a draft.
- **Legal bases.** Article-level citations per field, read from the official
  law texts (Schaffhauser Rechtsbuch, Fedlex), never from memory. A field
  without an explicit article is not automatically over-collection: the
  databank distinguishes "needed for the task" (KDSG Art. 4 Abs. 1 lit. b)
  from "neither a norm nor the task demands it".
- **Whose datum it is.** Each field records whether it describes a natural
  person, an organisation, a thing or an authority. Only a natural person's
  datum can be prefilled from the Einwohnerregister (once-only); a
  company's address cannot, even though it uses the same eCH element.
- **Legal remedies.** Per Verfahren: which Einsprache/Rekurs/Beschwerde a
  person has against the decision, with Frist and Instanz, quoted from the
  law PDF. Sectoral provisions where the cited law has its own; otherwise
  the general rule of the VRG, and the dashboard says which one it shows.
  A VRG default that no Prüfvermerk has yet confirmed is shown as exactly
  that — an unconfirmed default, not a verdict. The laws the DVSH model
  names count as candidates too: decisions of the Arbeitsinspektorat, for
  example, carry a Rekurs to the Regierungsrat within 30 days under the
  cantonal Verordnung zum Arbeitsgesetz (SHR 822.101), not the VRG default.
- **Code lists.** The official value lists from the eCH schemas (sex,
  marital status, residence permits, ...) and, per field, whether the form
  uses those codes or its own plain-text values.
- **Life events (Lebenslagen).** Services grouped the way people look for
  them, using the Themengruppen of the official Swiss topic catalogue
  eCH-0049 (approved; one catalogue for private persons, one for
  businesses). Many groups are life situations — birth, moving house, a
  death, unemployment, retirement, becoming self-employed — others are
  topics such as taxes or energy. Every group is checked in the official PDF
  (kept in `quellen/ech-0049/`) under its own Themenbereich. Per group: which
  services and offices a person meets, how many answers are asked, and where
  the services overlap on the same datum (same eCH element, same party, same
  named role; documents, remarks and mis-mapped fields are never matched).
  The overlap describes the offer, not one person's burden: services can be
  alternatives nobody goes through together.
- **One datum, one name (Begriffe — «Eine Angabe, ein Name»).** For every
  datum with an eCH element
  that forms ask for under at least two labels: one proposed term (always a
  label that already exists in the forms, never an invented one) and each
  label classified as *angleichen* (same thing, different wording — rename
  in the form), *Rolle* (names whose or which datum, e.g. "Name
  Arbeitnehmer", "Adresse bisher" — fine as it is), *Feld aufteilen* (the
  field bundles data the standard keeps apart, e.g. "Strasse und Nr" — split
  it in the form) or *eCH-Zuordnung korrigieren* (the label means a
  different datum than the element the databank mapped it to — a databank
  fix, not the office's). Where no clean term exists, the proposal is marked
  *unter Vorbehalt* with its reason. Data asked under a single label are not
  checked yet, and the page says how many. Shown per Formular next to each
  field as well.
- **Standard divergences, per Formular.** For every form: which of its data
  are demanded differently than on the other forms — mandatory here but
  optional elsewhere, a different type or format for the same datum, its own
  value list where the standard defines codes — each with what this form
  does, what the rest of the corpus does, the field's legal basis (a
  different basis can justify the difference) and the concrete action. Kept
  apart from data that simply has no citable standard yet, which is a gap,
  not a divergence. Where the corpus itself is split with no clear practice,
  the form is not called the outlier: the entry says a cantonal decision is
  missing.
- **Handling rules.** 248 rules on storing, processing and disclosing
  personal data, from 44 laws: 8 data-governance laws (data protection,
  information security, archiving and electronic administration — the
  cantonal KDSG, KDSV, ISV and ArchivV, and the federal DSG, DSV, BGA and
  EMBAG, which bind federal bodies) and 36 sectoral laws. Every rule carries
  a quote checked word-for-word against the official law PDF. Retention
  periods are machine-readable, so deletion dates can be computed.
- **The register.** Per Formular: purpose, recipients, retention and DSFA
  status, structured like KDSG Art. 17b Abs. 2. (The duty to keep such a
  register applies under Art. 17b only to Polizei, Staatsanwaltschaft and
  Justizvollzug; for every other office the register here is a management
  tool, and the dashboard says so.)
- **Digitalisation.** Per Formular: submission channel, signature
  requirement, required enclosures, citizen effort, and what blocks a fully
  digital process.
- **How the Formulare look (Gestaltung).** Measured on the published file of
  each of the 431 Formulare that have one — 348 PDF, 60 Word and 20 Excel
  files; the other 3 are in an old format (two .doc, one .xls) and cannot be
  read — in 21 Merkmale and five groups: Schrift (typeface, base size, small
  print, embedded fonts, mixed typefaces), Farben (accent colour, several
  colour families), Barrierefreiheit — Mindestmerkmale (structure tags,
  document language, document title, field descriptions, text layer,
  headings in Word), Kontaktangaben (whether a printed phone number says
  whose it is, how the numbers are written, fax numbers, personal e-mail
  addresses) and Aufbau (page format, edition mark, page numbers, sender on
  the first page). The yardstick is the practice of the measured Formulare,
  because the canton's corporate-design manual is not in the databank: a
  value shared by at least two thirds of the Formulare measured for a
  Merkmal (and at least 30 of them) is the practice — Arial (376 of 423), no
  accent colour (277 of the 344 PDF measured for it), A4 portrait (395 of
  428), page numbers on multi-page PDF and Word Formulare (186 of 259).
  Where no value reaches two thirds, no Formular is called the outlier and
  the Merkmal waits for the canton. Five Merkmale do today: base size, how
  phone numbers are written, edition mark and sender show no clear
  practice, and for small print the databank knows no rule on a minimum
  font size. For none of them does a rule lie before the databank; whether
  the canton has laid one down, it does not know. Accessibility is measured
  only as machine-checkable Mindestmerkmale: a missing one is a Lücke, a
  present one is no proof of accessibility, and none of it is a test
  against eCH-0059, WCAG or PDF/UA; 57 of the 348 PDF carry structure tags,
  a document language and a document title that names the Formular
  together. The page counts 220 Abweichungen from the practice and 1,042
  Lücken (Formular × Merkmal) on 420 Formulare; most Lücken are properties
  of the file rather than its visible look — 339 concern the document title
  in the file properties (missing, a placeholder or naming something else),
  229 the field descriptions of a fillable PDF. Not measured: anything inside an
  image (logos and their colours, text and numbers in images — 251 of the
  348 PDF carry an image on the first page), which logo a Formular carries,
  and the 42 eFormulare, which have no file of their own and take the look
  of the platform. E-mail addresses are never stored, only their type and
  domain. The files were measured on 2026-10-04 (method `gestaltung-2`).

The dashboard also has: a **Handlungsbedarf** board — per Dienststelle, with
the office's contact — listing what an office changes on its form (red: a
field without legal basis, a datum demanded differently than on the other
forms, a label to align or a field to split, an outdated form) and what the
canton decides (amber: no eCH standard in force, mandatory or optional split
across the forms, Aufgabenbedarf open, DSFA decision, undecided duplicate),
plus one line per office on the Schutzstufe the canton has not set yet; a
**Recherche der Databank** page with the databank's own homework (legal basis
still to research, the KDSG Art. 5 basis of a besonders schützenswerte
Angabe, purpose, recipients, eCH mapping or a superseded standard, overdue
online check, a remedy not determined or its default unconfirmed, an
unbacked Verfahren outcome); a CSV export that holds all of these points; a
**Datenfluss** map (which Dienststelle passes data to which recipient, from
the article-backed disclosures), a **Bürgersicht** (what the Datentresor
holds about three synthetic persons, seen from their side), and a search box
over everything: laws, articles, fields, rules, recipients, enclosures,
standards, offices.

## How the data is verified

Machine-derived entries only enter the database through checks: a citation
must exist in an ingested law article, an eCH element must exist in the
official XSD, a rule quote must appear verbatim in the law PDF. Anything
that fails is rejected. Every citation shows its verification level, and
"not yet researched" is never mixed up with "proven to have no legal basis".
The databank currently holds 6,334 curated citations: 2,900 to federal law,
whose articles were read from the official Fedlex text when the law was
ingested (level `verified`), and 3,434 to cantonal law, read from the
official PDF of the Schaffhauser Rechtsbuch (level `Gesetze-PDF`); none is
unverified. The level is the cited article's, one column for every surface;
it records where the article text came from at ingest, not a later re-check
against the live text, and no cantonal article carries `verified`. The DVSH
model and the SHEP portal are the sources of truth for service facts and
were read strictly without changing anything.

The verdict files the loaders read (one JSON per Formular from the review
passes) are transient and are not kept in the repository. What they produced
is inspectable in the database itself: `data_field.derived_by`,
`last_checked` on `article` and `data_field_legal_basis`, the `panel_review`
table (2,168 second opinions; 7 of them still «offen»: 5 items added on
2026-09-26 that await the second review and 2 where the second review
disagreed) and `begriff_vorschlag.herkunft`. The single
corrections that were verified by hand are kept under `quellen/korrekturen/`
and `quellen/rechtsmittel/`, with the script that applies them. One check a
peer can run: every article a field citation points to must carry a
`verified` or `Gesetze-PDF` level —

```sql
SELECT count(*) FROM data_field_legal_basis d JOIN article a ON a.id = d.article_id
WHERE a.last_checked NOT LIKE 'Gesetze-PDF%' AND a.last_checked NOT LIKE 'verified%';
-- 0
```

**Datenstand.** The dashboard's home page names the date each layer was
true, not only the build date. Currently: DVSH and SHEP harvest 2026-09-03;
last full online check of the Formulare against sh.ch 2026-07-31, with a
partial re-check on 2026-09-26 (97 Formulare: 94 confirmed current, 3
flagged as probably revised); eCH XSD sweep 2026-09-26 (116 standards looked
up, 82 of them publish their own XSD). 409 of the 473 Formulare have been
checked online at all; for 312 of them the re-check is overdue and 64 have
never been checked — 42 of them eFormulare, which have no file on sh.ch to
compare, and 22 Formulare with a file. «Recherche der Databank» lists these
as open points.
The page «Gestaltung der Formulare» names its own date: the Formular files
were measured on 2026-10-04. The measurement stores facts only;
`validate_db.py` refuses a row measured on another file than the current
one, and the comparison stops the export when its own sums do not add up.
The figures in this README are those of the build of 2026-10-04; the start
page and the dashboard always show the current ones.

## The Datentresor

`datentresor.db` shows how the collected data could actually be stored:
1,200 synthetic residents, 10,000 cases, 184,915 stored values, and 19,664
further uses in later cases that reused an earlier value instead of asking
again (figures from the once-only ledger of the `datentresor.db` built on
2026-09-27, see its `meta` table; `./build.sh --tresor` prints the new ones).
The rules are enforced by the database itself: a
person's own datum is stored once and reused (once-only; a company's or an
authority's address is stored per case, not as the person's), sensitive
values (8,296 in this build) are AES-256-GCM encrypted with the key kept
outside the database, and triggers refuse unencrypted sensitive values,
wrong formats, hard deletes, any change to the access log, and any value
that carries neither an article, nor a consent (given only for proven
over-collection), nor an explicit label — «Aufgabenerfüllung» (needed for
the task), «aufgabennotwendig — Grundlage nach KDSG Art. 5 Abs. 1 noch nicht
benannt» (a besonders schützenswerte Angabe whose Art.-5 basis is still
open), «Rechtsgrundlage zu ermitteln» or «Aufgabenbedarf noch nicht
beurteilt». An unresearched basis is therefore stored as a labelled gap,
never as consent: 138,123 values cite an article, 461 rest on consent,
46,331 carry one of those labels. Views answer the standard data-protection
questions directly: `v_auskunft`, `v_loeschliste`, `v_verzeichnis`.

`datentresor.key` is deliberately not in the repository. In the committed
`datentresor.db` the encrypted values therefore appear as `[verschlüsselt]`
in `v_auskunft` and cannot be decrypted. Rebuilding (`./build.sh --tresor`)
creates a fresh key locally and re-encrypts; it needs a Python with the
`cryptography` package (the project uses `.venv/bin/python3`, which
`build.sh` picks up automatically). Without it the build falls back to a
labelled demo cipher and records that in the `meta` table. The file is not
byte-reproducible because the AES-GCM nonces are random, so every rebuild
adds a new copy of about 17 MB to the repository history for good. Rebuild it
only when the vault logic or the field layer it samples has changed
materially; the file is just under GitHub's 50 MiB warning size, and GitHub
refuses files over 100 MiB.

All data in `datentresor.db` is synthetic (its `meta` table says so): the
residents are drawn from fixed name lists with a fixed seed. The rest of the
repository holds only what the canton itself publishes: office contact
details from the DVSH model and the SHEP portal (some of them name a staff
member), and the official Formular files exactly as downloaded from sh.ch,
including the metadata the files carry.

## Building

```bash
./build.sh            # every generated surface from citygov.db
./build.sh --tresor   # additionally rebuild datentresor.db
./build.sh --pdf      # additionally write dossiers/*.pdf (local only)
```

One command rebuilds everything in dependency order: `init_register.py`
(rewrites the derived table `canonical_attribute` and the derived column
`data_field.format_code` inside `citygov.db`, refreshes `format_pattern` and
adds any new Dienststelle name to `dienststelle` — the only step that writes
to the database) → with `--tresor`, `build_datentresor.py` (`datentresor.db`,
built before the export reads it for the Bürgersicht) → `export_json.py`
(`data_export.json`, with the comparison of the Gestaltung from
`gestaltung_export.py`, and today's entry in `verlauf.json`; both are written
only after its own gates passed — every figure with parts sums to its total,
every Dienststelle adds up, no layer failed silently — otherwise it ends with
«ABBRUCH … nichts geschrieben») → `theme.py --check` (the shared look: every
text colour reaches 4.5:1 on its backgrounds, no colour, size or font literal
is left in a page generator) → `build_dashboard.py` (`dashboard.html`; stops
with «ABORT» on an export that lacks a figure the page reads instead of
computing) → `build_flows.py` (`flows.html`) → `export_llm.py` (the
`citygov_*` exports) → `export_ech_schema.py` (`citygov_ech_schemas.json`) →
`export_dossiers.py` (`dossiers/`) → `build_index.py` (`index.html`,
`404.html`) → `validate_db.py` → `check_pages.mjs`, the automatic page
check. The build reads nothing outside the repository. It prints the sizes of
`dashboard.html`, `flows.html`, `data_export.json` and `citygov_llm.json`,
then the result of the page check, and writes `logs/citation_todo.txt`
(every ingested law article not at level `verified`) locally; `logs/` is not
tracked. A `--pdf` build adds a PDF column to `dossiers/index.html`; run a
plain `./build.sh` before committing, so the published index does not link
PDFs that are not in the repository. A second run on the same data
reproduces every generated page and export byte for byte apart from the
`generated_at` stamp; `citygov.db` is the exception — `init_register.py`
recreates its derived rows on every run, so the file's bytes change while its
content does not, and `git status` lists it after every build.

**The page check.** The last step, `node scripts/check_pages.mjs`, opens the
built pages in a local headless Chrome (driven through a pipe, without
network) and fails the build with one plain message per finding: an inline
script that does not parse, a page that does not start or writes an error to
the console, a request to another host, a bar or a list whose numbers do not
add up to the total it states, a text colour below 4.5:1, a link in the
browser's default blue, text below 12 px, a `dashboard.html` of 95 MiB or
more (GitHub refuses files over 100 MB; below that, size is no goal), or something clickable that the keyboard cannot reach. It takes a few
seconds; `--only <check>`, `--verbose` and `--breite <px>` (a window of
another width) narrow or widen it. Without Node or Chrome it prints
«Seitenprüfung übersprungen: Node oder Chrome nicht gefunden» and the build
succeeds; a Chrome that is found but does not start fails the build with the
cause («Seitenprüfung fehlgeschlagen: …» — in a container set
`CHROME_FLAGS=--no-sandbox`; `CHECK_PAGES=skip` builds without the check on
purpose). `scripts/README.md` lists every check and what clears it.

Loading new data is a different job. The loaders under `scripts/`
(`load_*.py`, `ingest_*.py`, `sweep_ech_xsd.py`, `run_begriffe.py`,
`scan_gestaltung.py`, and the one-off `migrate_*.py` corrections) each write
to a staging copy, validate, and only then replace the database, so a failed
loader step leaves `citygov.db` as it was before that step. `run_begriffe.py`
is a chain of such steps, each swapped on its own: when a later step fails,
the earlier ones stay applied, so rerun the whole chain. `sweep_ech_xsd.py`
keeps the XSD files it downloaded even when its database write fails.
`scripts/README.md` gives their order, from the law chain to the flows, and
a one-line purpose for every script.

**Requirements.** Python 3. `./build.sh` itself needs only the standard
library, except `--tresor`, which needs the `cryptography` package, and
`--pdf`, which needs Google Chrome at its macOS location
(`/Applications/Google Chrome.app`). The page check at the end of `./build.sh`
needs Node (16 or newer) and a local Chrome, Chromium or Edge; without them
it is skipped and the build still succeeds. The loaders and harvesters need
`pypdf` and `openpyxl` (`scan_gestaltung.py`, the measurement of the
Gestaltung, refuses to start without pypdf; it was written and tested with
pypdf 6.13); the Datentresor build needs `cryptography` — all
three are in `requirements.txt`:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

`build.sh` uses `.venv/bin/python3` when it exists; run the loaders with it
too.

The loaders need two more things that are not in this repository. First,
macOS: they read law PDFs through `scripts/extract_law.py`, which uses
PDFKit via `osascript` (JavaScript for Automation), and Word Formulare
through `textutil`. `build_gesetze_index.py`, `ingest_laws.py`,
`ingest_fed.py`, `load_data_rules.py`, `load_rechtsmittel.py` and
`load_themenkatalog.py` find no text on other systems, so they skip or
reject. Second, the canton's source folders next to the repository:
`../Gesetze/` (the law PDFs, federal ones in `../Gesetze/Bund/`),
`../Verwaltung/` (the Formular files as the offices hold them, read by
`ingest_new.py`) and `../DVSH/` (the saved DVSH harvests).

## Known gaps

- **Legal bases.** The 73 Formulare taken from the DVSH model (42 eFormulare
  built from its form definitions and 31 files from its asset store) have
  their standards mapping but not yet their article-level legal bases: 1,098
  fields on 74 Formulare are marked "zu ermitteln" — the 73 DVSH-sourced
  ones entirely (1,088 fields) plus 10 fields of one older form.
- **Cantonal decisions.** Schutzstufen and DSFA decisions are the canton's
  to make and stay empty until then.
- **Legal remedies.** A Verfahren outcome is modelled for 172 of the 473
  Formulare; the other 301 have none yet. Of the 172, 104 carry a quoted
  remedy — 20 from a sectoral provision, 84 the general VRG rule, and 31 of
  those 84 are still the default without a Prüfvermerk confirming that no
  sectoral provision applies. 28 end without an appealable decision, 16 have
  an outcome the DVSH text does not back (so the remedy question is not
  reached), and 24 have none: 18 were assessed and could not be decided from
  the cited law (mostly commercial-register and notarial acts under federal
  law), 6 have not been looked at yet. The dashboard says which is which.
- **Standards.** eSH is a draft and shrinks as eCH assignments take fields
  over. Where the corpus is split on how a datum is demanded, the entry asks
  for a cantonal decision instead of naming an outlier.
- **Naming.** Data asked under a single label are not checked for a common
  term yet; the Begriffe page says how many.
- **Currency.** 312 Formulare are overdue for their online re-check and 64
  have never been checked against sh.ch: 22 Formulare with a file and the 42
  eFormulare, which have no file there to compare (see Datenstand above).
- **One DVSH eFormular not loaded.** Service 640 (Atelierstipendien in
  Berlin, DVSH 206, split off on 2026-09-27) has its own DVSH eFormular
  definition with 15 fields. `scripts/link_dvsh_eforms.py` would add it as
  a 43rd eFormular; it has not been run since the split, so the service is
  counted among those without a Formular.
- **Guided flows** exist for 57 of the 473 Formulare.
- **Gestaltung der Formulare.** The yardstick is the practice of the
  measured Formulare, not the canton's corporate design, whose manual is not
  in the databank: «entspricht der Praxis» does not mean that a Formular
  meets a rule, nor «weicht ab» that it breaks one. Five Merkmale wait for
  the canton: four show no clear practice, and the databank knows no rule
  on a minimum font size; whether the canton has laid down a rule for any
  of them, the databank does not know. Accessibility is checked only for
  its machine-checkable Mindestmerkmale; reading order, alternative texts,
  contrast and the quality of tags and field descriptions are not checked.
  Nothing inside an image is measured (logos, their colours, text in
  images), and federal Formulare and those of other cantons, foreign
  authorities or third parties are measured like the canton's own. Not
  measurable: the 3 files in an old format, and the text of the 2 scanned
  PDF and of 2 PDF that store their text unreadably. The 42 eFormulare are
  not judged. The measurement is not part of `./build.sh`: after a new
  Formular or a changed file, run `scan_documents.py` and then
  `scan_gestaltung.py`. A Formular without a row — a new one, or one whose
  changed file `scan_documents.py` has registered — is shown as «noch nicht
  gemessen».
- **Retired layer.** The auto-draft layer of 2026-06 (tables `form_field`,
  `field_mapping`, `requirement` and their links) is retired: the curated
  `data_field` layer replaced it, and its field drafts are not exported. The
  tables stay in the database for the record; its 388 per-service notes
  remain in `citygov_llm.json` (`services[].findings`), marked there as
  legacy text.

The Handlungsbedarf board and «Recherche der Databank» together list every
open point by Dienststelle (the CSV export holds all of them); the dashboard
shows each one where it occurs.
