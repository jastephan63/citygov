# citygov — Compliance-Databank Kanton Schaffhausen

> **▶ Open the dashboard: <https://jastephan63.github.io/citygov/dashboard.html>**
> — nothing to install, runs in any current browser (Chrome, Edge, Firefox, Safari).
> Start page with the dossiers and the guided forms: <https://jastephan63.github.io/citygov/>

A database of the canton's administrative services. For each service it
records: the laws behind it (down to the article), the data its Formulare
collect (down to the single field), the standard each datum maps to (eCH, or
the draft cantonal standard eSH), the rules for handling that data (storage,
retention, disclosure), and how far the service is from being fully digital.

Gaps are shown as gaps. If a legal basis is missing or unverified, the
dashboard says so instead of hiding it.

It is written for two readers: peer administrations building the same kind
of databank, and an LLM agent that has to process cantonal services from it
— which is why every statement has to be precise, sourced and never silently
wrong.

## Opening the dashboard

**In the browser — the easy way.** Open
<https://jastephan63.github.io/citygov/> (start page) or go straight to
<https://jastephan63.github.io/citygov/dashboard.html>. The site is this
repository served by GitHub Pages, so it always shows the latest pushed
version, and the links to the dossiers and to the original Formular files
work there too. The dashboard is one page with all data built in: about
5 MB travel over the network, and the browser then needs a few seconds to
read the data — the page says so while it loads.

**Not on github.com itself.** GitHub cannot display a file this large, and
its «Raw» button shows the file as plain text (source code) instead of the
dashboard. Use the link above instead.

**An offline copy of the dashboard alone.** On the start page, right-click
«Dashboard öffnen» and choose «Save link as…» (or «Download linked file»),
then double-click the saved `dashboard.html` (Mac: Ctrl-click the link; in
Safari the menu item is «Download Linked File»). It runs without internet in
any current browser. In such a single copy the links to dossiers, Formular
files and guided forms open on the website; fully offline they need the whole
repository (next option).

**Everything, offline.** Click the green **Code** button at the top of this
page and choose **Download ZIP**: about 180 MB to download, about 390 MB
unpacked — about 150 MB of that is the original Formular files in `formulare/`.
Unzip it and double-click `index.html` (start page) or `dashboard.html`; everything, including the dossiers and the original Formular files, then works without internet.
Or clone it (about 260 MB to transfer, growing with every update, since the
history keeps each version; `git pull` brings updates later):
```bash
git clone https://github.com/jastephan63/citygov.git
```

**If a browser is slow with the file.** Some browsers handle a page this
size better over http than from a double-clicked file. In the folder, run
```bash
python3 -m http.server 8917
```
and open `http://localhost:8917/`. Any other static file server works too.

`datentresor.db` opens with any SQLite client, for example
`sqlite3 datentresor.db` or DB Browser for SQLite.

## How the dashboard is organised

- **The data standard comes first.** The start page opens with three figures:
  how many data points carry an eCH element, how many are demanded the same
  way as on the other forms, and how many fields still carry a deviating name.
  Legal-basis and register gaps follow, then the open points.
- **Three entry points**, one per reader: *Für Dienststellen* (what an office
  has to change on its forms — one page per Dienststelle with its most
  important actions, printable as a brief), *Für den Kanton* (what has to be
  decided) and *Methode & Quellen* (how the databank is built).
- **The colour says who acts next**, on every page: green settled, red the
  Dienststelle changes its form, amber the canton decides, grey the databank
  still has to research it. Open points are gaps, not findings of a breach.
  The Gestaltung page keeps these colours and says in its own words what
  they mark there (see below).
- **Priorities**: data standard, then legal basis, then procedure & register,
  then inventory & currency. The databank's own research homework has its own
  page («Recherche der Databank») and is kept off the offices' lists.
- **Datenmodell & Once-Only.** A sidebar group of its own, right after the
  data standard, with two pages that open like the start page: the question
  «Wo anfangen?» and one card per topic, each with one figure. *Datenmodell*
  (`#datenmodell`) shows whose Angabe each data point is (the 26 roles with
  their counts, the parties per Formular, the reasons of «unklar», and how
  the layer was made and checked — rules, judgement from the Formular text
  with a quote, second review, audit), one element per Angabe and role (the
  27 concepts, folded, each with its cells, the Vorschlag and the Formulare
  that use another element), the permanent identifiers (counts per kind,
  the scheme, a worked example, the export contract with the version and
  schema of every export), the edition of every cited law, and the
  change-impact explorer: pick a law, see its cited articles and, per
  article, the Formulare that cite it. *Was Register schon wissen*
  (`#onceonly`) opens with one card per register group (Einwohnerregister,
  Unternehmen, Gebäude und Grundstücke, Steuern, Fahrzeuge, Zivilstand,
  weitere Register), then the Beilagen a register issues, the model
  estimate of the time saved and the open legal questions; per register it
  shows the holder, level, content, key, eCH standards and sources and what
  it holds of the Formulare. Its figures say what a register holds, never
  that an office may fetch it. Every section has a shareable address
  (`#datenmodell/all/<section>` with `parteien`, `konzepte`, `kennungen`,
  `gesetzesstand`, `wirkung`, a concept `k-<code>`, a law `g-<law id>`, an
  article `a-<article id>`; `#onceonly/all/<section>` with `register`,
  `g-<group>`, `r-<register>`, `beilagen`, `zeit`, `offen`). Every Formular
  has two more folded panels, «Parteien» and «Was Register schon wissen»
  (plus «Eine Angabe — ein Element» where one of its data points uses
  another element than the Vorschlag of its concept), and shows its
  permanent identifier once, under its title, with a copy button;
  every Dienststelle brief has a section «Datenmodell und Register»; every
  law and article — on the rules page, in the legal bases of a field, in the
  law view — carries its edition chip («aktuell», «neuerer Stand seit …»,
  «Stand unbekannt») and a link «betrifft N Datenpunkte in M Formularen ›»
  to the explorer. The start page names both pages in its «Auch:» line; its
  headline cards and doors are unchanged, and the concept findings are not
  part of the headline figures, the open points or the Handlungsbedarf.
- **Gestaltung der Formulare — a part of its own.** How the Formulare look
  and are presented, compared with each other: Schrift, Farben, the
  Mindestmerkmale of accessibility, Kontaktangaben and Aufbau. It has its
  own sidebar group «Erscheinungsbild», after the data standard and the
  data model, and opens like the start page: the question «Wo anfangen?» with seven doors —
  first the readers, *Je Dienststelle* and *Für den Kanton* (the Merkmale
  without a clear practice or rule), then the five groups. Per Merkmal the
  page shows the practice (or «keine klare Praxis»), the measured values as
  a neutral list, the findings in their colour and, folded, the Formulare
  concerned, each linked to its Formular view; the table *Je Dienststelle*
  keeps the order of «Für Dienststellen» (by Departement, A–Z) and counts
  Abweichungen and Lücken apart. Every section has a shareable address (e.g.
  `#gestaltung/all/barrierefrei`). Every Formular has a folded panel
  «Gestaltung» on its service page and in its Formular view, every
  Dienststelle brief a short section «Gestaltung ihrer Formulare»; the start
  page has one link line under its doors, and «Für den Kanton» one pointer
  to the Merkmale without a clear practice. In this part green is
  «entspricht der Praxis» or «vorhanden», red «weicht ab» or «Lücke» (a
  difference on the Dienststelle's Formular, no request to change it —
  whether a rule is broken, the databank cannot say), amber «keine klare
  Praxis» (no rule lies before the databank; the canton decides, once per
  Merkmal) and grey «nicht messbar» or «noch nicht gemessen» (open with the
  databank, no finding about the Formular); the measured values themselves
  carry no colour, and numbers are written with a decimal point like
  everywhere else. The texts describe what differs and never ask an office
  to change its Formular. The
  figures stay on this page: they are not part of the headline figures, the
  open points, the Handlungsbedarf or the priority tiers.
- **Trend**: every figure is compared with the previous snapshot in
  `verlauf.json`; notes explain jumps. Shares are shown with one decimal
  everywhere (68.4 %), so a small movement between two builds stays visible.
- **Terms and contacts.** A glossary on «Methode & Quellen» explains the
  databank's terms (Datenpunkt, eCH-Element, Teilfeld, Divergenz, Partei,
  Rolle, Kennung, Gesetzesstand, Register, Once-Only, Vorbefüllung …); the
  headline cards explain the same terms on a tap. A Dienststelle's contact is
  written the same way on every page, in the dossiers and in the guided
  forms: «Kontakt (laut DVSH): Adresse · Tel. … · E-Mail …», the stored
  values verbatim, telephone and e-mail as links.
- **One look.** Fonts, colours, the four tones and the six text sizes are
  defined once (`scripts/theme.py`) and used by the dashboard, the start page,
  the dossiers and the guided forms; every text colour reaches a contrast of
  4.5:1 and no text is smaller than 12 px — the page check at the end of the
  build measures both.
- **Prototypes** (the synthetic Datentresor view, the guided forms) sit in a
  separate «Werkstatt» section; the eSH standard is marked as a draft wherever
  it appears.

## What the data covers

- **Services and Formulare.** The unit is the service as modelled in the
  canton's service model (DVSH); Formulare belong to services, and a service
  can have several. Since 2026-09-27 every DVSH service whose model declares
  its own file or procedure has its own row (the evidence per row is in
  `quellen/korrekturen/dvsh_aufteilung_2026-09-27.json`); 5 rows carry several
  DVSH services that all name the same file, under a name taken from DVSH
  wording. Of the 491 services, 324 are linked to their DVSH entry, 7 are
  modelled in DVSH but missing from the current harvest (shown as
  «DVSH-Modellierung nicht in der Databank»), and 160 are services the DVSH
  model does not contain yet — kept as they are, never force-fitted. 75
  services have no Formular: 72 DVSH services, most of them reached through
  an eFormular without field definitions, by e-mail, phone, an external link
  or in person, and 3 of the 7 whose DVSH entry is missing. One of the 72,
  service 640 (DVSH 206, split off on 2026-09-27), does have a DVSH
  eFormular definition with 15 fields that has not been loaded yet (see
  «Known gaps»).
- **Data fields.** Each Formular's fields, broken down to atomic parts
  (Name, Vorname and Geburtsdatum separately, not just "Personalien").
- **Standards.** The eCH catalogue (290 standards, about 9,700 elements)
  plus eSH, a draft cantonal standard for everything eCH does not cover.
  eSH is always marked as a draft.
- **Legal bases.** Article-level citations per field, read from the official
  law texts (Schaffhauser Rechtsbuch, Fedlex), never from memory. A field
  without an explicit article is not automatically over-collection: the
  databank distinguishes "needed for the task" (KDSG Art. 4 Abs. 1 lit. b)
  from "neither a norm nor the task demands it".
- **Whose datum it is.** Each field records whether it describes a natural
  person, an organisation, a thing or an authority. Only a natural person's
  datum can come from the Einwohnerregister (once-only); a company's address
  cannot, even though it uses the same eCH element. Which person it is — the
  applicant, a spouse, a child — says the party layer below; only the
  applicant's own data are prefilled.
- **Legal remedies.** Per Verfahren: which Einsprache/Rekurs/Beschwerde a
  person has against the decision, with Frist and Instanz, quoted from the
  law PDF. Sectoral provisions where the cited law has its own; otherwise
  the general rule of the VRG, and the dashboard says which one it shows.
  A VRG default that no Prüfvermerk has yet confirmed is shown as exactly
  that — an unconfirmed default, not a verdict. The laws the DVSH model
  names count as candidates too: decisions of the Arbeitsinspektorat, for
  example, carry a Rekurs to the Regierungsrat within 30 days under the
  cantonal Verordnung zum Arbeitsgesetz (SHR 822.101), not the VRG default.
- **Code lists.** The official value lists from the eCH schemas (sex,
  marital status, residence permits, ...) and, per field, whether the form
  uses those codes or its own plain-text values.
- **Life events (Lebenslagen).** Services grouped the way people look for
  them, using the Themengruppen of the official Swiss topic catalogue
  eCH-0049 (approved; one catalogue for private persons, one for
  businesses). Many groups are life situations — birth, moving house, a
  death, unemployment, retirement, becoming self-employed — others are
  topics such as taxes or energy. Every group is checked in the official PDF
  (kept in `quellen/ech-0049/`) under its own Themenbereich. Per group: which
  services and offices a person meets, how many answers are asked, and where
  the services overlap on the same datum (same eCH element, same party, same
  named role; documents, remarks and mis-mapped fields are never matched).
  The overlap describes the offer, not one person's burden: services can be
  alternatives nobody goes through together.
- **One datum, one name (Begriffe — «Eine Angabe, ein Name»).** For every
  datum with an eCH element
  that forms ask for under at least two labels: one proposed term (always a
  label that already exists in the forms, never an invented one) and each
  label classified as *angleichen* (same thing, different wording — rename
  in the form), *Rolle* (names whose or which datum, e.g. "Name
  Arbeitnehmer", "Adresse bisher" — fine as it is), *Feld aufteilen* (the
  field bundles data the standard keeps apart, e.g. "Strasse und Nr" — split
  it in the form) or *eCH-Zuordnung korrigieren* (the label means a
  different datum than the element the databank mapped it to — a databank
  fix, not the office's). Where no clean term exists, the proposal is marked
  *unter Vorbehalt* with its reason. Data asked under a single label are not
  checked yet, and the page says how many. Shown per Formular next to each
  field as well.
- **Standard divergences, per Formular.** For every form: which of its data
  are demanded differently than on the other forms — mandatory here but
  optional elsewhere, a different type or format for the same datum, its own
  value list where the standard defines codes — each with what this form
  does, what the rest of the corpus does, the field's legal basis (a
  different basis can justify the difference) and the concrete action. Kept
  apart from data that simply has no citable standard yet, which is a gap,
  not a divergence. Where the corpus itself is split with no clear practice,
  the form is not called the outlier: the entry says a cantonal decision is
  missing.
- **Handling rules.** 248 rules on storing, processing and disclosing
  personal data, from 44 laws: 8 data-governance laws (data protection,
  information security, archiving and electronic administration — the
  cantonal KDSG, KDSV, ISV and ArchivV, and the federal DSG, DSV, BGA and
  EMBAG, which bind federal bodies) and 36 sectoral laws. Every rule carries
  a quote checked word-for-word against the official law PDF. Retention
  periods are machine-readable, so deletion dates can be computed.
- **The register.** Per Formular: purpose, recipients, retention and DSFA
  status, structured like KDSG Art. 17b Abs. 2. (The duty to keep such a
  register applies under Art. 17b only to Polizei, Staatsanwaltschaft and
  Justizvollzug; for every other office the register here is a management
  tool, and the dashboard says so.)
- **Digitalisation.** Per Formular: submission channel, signature
  requirement, required enclosures, citizen effort, and what blocks a fully
  digital process. «Aus dem Einwohnerregister vorbefüllbar» counts the
  required answers that `citygov_prefill.json` and the guided forms would
  prefill from the applicant's profile: an Angabe a quoted rule of the
  Einwohnerregister names (RHG Art. 6, Gemeindegesetz Art. 88 Abs. 2), that
  belongs to the applicant (party Gesuchsteller/in, a natural person), that
  is not ambiguous within that party and that asks for the value the
  register holds today: 841 answers on 159 Formulare (870 with the optional
  ones; 336.4 model minutes). The last condition is the time rule of
  2026-10-05: a label that asks for an earlier, a later or a changed value
  («Frühere Wohnorte», «Adresse(n) während der letzten zwei Jahre»,
  «Zivilstand neu», «… seit», «Zuzug») is never filled from the register's
  current entry, unless the element itself names that value (the Zuzug
  date, the date of the civil status); a death date never. 90 answers with
  the register mark, on 33 Formulare, carry such a label. The published
  count was 1,639 answers on 281 Formulare (655.6 model minutes) until
  2026-10-04. By that former rule it would be 1,703 today; of these, 756 are
  another person's answers (a child, a spouse, an employee, a deceased
  person …), 38 belong to a party not yet settled, 73 name no element a
  quoted register rule names (a PIN, an Abrechnungs-Nr.), 4 are ambiguous
  and 6 ask for another time; 15 are added because a quoted rule names
  them. Whether the register may deliver a spouse's or a child's data is the
  canton's decision; until then they are not counted.
- **Permanent identifiers.** Every service, Formular, data field, part,
  canonical Angabe (an eCH element with its context, or an eSH key), law,
  article and handling rule has an identifier that never changes meaning:
  26,644 active today (491 services, 473 Formulare, 5,991 data fields, 7,676
  parts, 2,766 Angaben — 862 eCH, 1,904 eSH —, 150 laws, 8,849 articles, 248
  rules) and 3 «entfallen»: two article rows that were ingest artefacts,
  removed on 2026-10-05, and the Angabe eCH-0011 religionData, which no data
  point carries since an eCH correction of the same day. The scheme names no web address, e.g.
  `sh:formular:<slug>:feld:11:teil:2`,
  `sh:angabe:eCH-0044:firstName:personIdentificationType`,
  `sh:gesetz:sr-741.51:art-78`,
  `sh:gesetz:shr-120.100:art-14:regel:bekanntgabe-sektoral`. A field keeps
  its identifier through a rename only on evidence that a deleted and
  re-inserted row cannot fake — the same eCH element or eSH key at the same
  place, or for a field without one the same definition; when unsure, the
  old identifier becomes «entfallen» and the field gets a new one. An
  identifier whose object is gone stays, marked «entfallen», and is
  published with its date and reason (`kennungen` in `data_export.json`,
  `meta.kennungen` in `citygov_llm.json`); none is ever reused or pointed at
  another object (`scripts/kennungen.py`, table `kennung`, whose gates are
  triggers in the database; the build refuses to mint into a lost table, and
  the database check reports every published identifier the table lacks). The numeric ids are not stable — `canonical_attribute` is
  renumbered on every build — so every export and the Datentresor carry the
  identifiers, and every export its version under the export contract
  (`exportvertrag.json`, a JSON Schema per export under `schema/`; see
  «What is in here»). The base address for resolvable links is still to be chosen

  9,601 data points (80.6 %) have a party, 2,313 are «unklar». Stage B1,

  with the reason). Per concept and party role — a role together with its
  entity type, so the applicant as a natural person and as «Person oder
  Organisation» are two cells — the element that at least two thirds of
  the cell's data points use is the «Vorschlag», if the cell has at least
  10 data points; otherwise the canton decides. 4,449 data points on 440
  Formulare belong to a concept: 2,763 in the 84 cells with a Vorschlag
  (2,533 use it; 230, on 128 Formulare, use another element or standard),
  1,182 in the 263 cells the canton decides (12 without a two-thirds
  practice, 251 with fewer than 10 data points), 488 without a party yet
  and 16 of a party whose own Angabe the concept is not; 59 data points
  whose element the naming layer found wrong are counted apart. The

  it. The figures stay on the page «Datenmodell», where each concept lists
  the Formulare that use another element: they are not part of the

- **Law editions and change impact.** For each law, the edition («Stand»)

  721.100).

  what is affected»: per law and per article the citations, data fields,

- **What registers already hold (Register, Once-Only).** A catalogue of 18 Swiss

  register holds it — an upper bound by standard (6,152 data points), the
  Angabe named by a source, and confirmed when the party fits too, or by an

  dog, the GWR not for the heating or the areas a permit or a notification

  applicant's own tax return or an annotated plan, a number (the
  Steuerregister-Nummer), a figure about the Gemeinde or a creditor's copy

  original or an identity proof is attributed but not counted as saved.
  «Hält» on the dashboard means exactly this: a quoted official source
  names the Angabe or the document as the register's content (and, at the
  level «bestätigt», the kind of party fits). It says nothing about whether
  an office «beziehen darf» — may fetch it from the register. That is a
  second step, governed by the law of the register (for cantonal offices
  KDSG Art. 8 Abs. 1, for federal registers federal law), and the databank
  records only what it can quote: an ingested article counts as a
  candidate (GBV Art. 26 and 28, HRegV Art. 11, StG Art. 127 Abs. 2 and
  Art. 128) or as a limit (StG Art. 127 Abs. 1); everywhere else access is
  «offen — rechtlich zu klären», for the canton's lawyers. The time the

  minutes per required answer, 5 per Beilage): at most 1,169.4 minutes
  (1,911 required answers and 81 Beilagen — including other parties'
  answers and registers whose access is open; the prefill rule keeps 336.4
  of them), summed over one pass through every Formular; case numbers per service are the canton's
  data and are not available (`scripts/register_katalog.py`,
  `scripts/register_map.py`).
- **How the Formulare look (Gestaltung).** Measured on the published file of
  each of the 431 Formulare that have one — 348 PDF, 60 Word and 20 Excel
  files; the other 3 are in an old format (two .doc, one .xls) and cannot be
  read — in 21 Merkmale and five groups: Schrift (typeface, base size, small
  print, embedded fonts, mixed typefaces), Farben (accent colour, several
  colour families), Barrierefreiheit — Mindestmerkmale (structure tags,
  document language, document title, field descriptions, text layer,
  headings in Word), Kontaktangaben (whether a printed phone number says
  whose it is, how the numbers are written, fax numbers, personal e-mail
  addresses) and Aufbau (page format, edition mark, page numbers, sender on
  the first page). The yardstick is the practice of the measured Formulare,
  because the canton's corporate-design manual is not in the databank: a
  value shared by at least two thirds of the Formulare measured for a
  Merkmal (and at least 30 of them) is the practice — Arial (376 of 423), no
  accent colour (277 of the 344 PDF measured for it), A4 portrait (395 of
  428), page numbers on multi-page PDF and Word Formulare (186 of 259).
  Where no value reaches two thirds, no Formular is called the outlier and
  the Merkmal waits for the canton. Five Merkmale do today: base size, how
  phone numbers are written, edition mark and sender show no clear
  practice, and for small print the databank knows no rule on a minimum
  font size. For none of them does a rule lie before the databank; whether
  the canton has laid one down, it does not know. Accessibility is measured
  only as machine-checkable Mindestmerkmale: a missing one is a Lücke, a
  present one is no proof of accessibility, and none of it is a test
  against eCH-0059, WCAG or PDF/UA; 57 of the 348 PDF carry structure tags,
  a document language and a document title that names the Formular
  together. The page counts 220 Abweichungen from the practice and 1,042
  Lücken (Formular × Merkmal) on 420 Formulare; most Lücken are properties
  of the file rather than its visible look — 339 concern the document title
  in the file properties (missing, a placeholder or naming something else),
  229 the field descriptions of a fillable PDF. Not measured: anything inside an
  image (logos and their colours, text and numbers in images — 251 of the
  348 PDF carry an image on the first page), which logo a Formular carries,
  and the 42 eFormulare, which have no file of their own and take the look
  of the platform. E-mail addresses are never stored, only their type and
  domain. The files were measured on 2026-10-04 (method `gestaltung-2`).

## How the data is verified

Machine-derived entries only enter the database through checks: a citation
must exist in an ingested law article, an eCH element must exist in the
official XSD, a rule quote must appear verbatim in the law PDF. Anything
that fails is rejected. Every citation shows its verification level, and
"not yet researched" is never mixed up with "proven to have no legal basis".
The databank currently holds 6,334 curated citations: 2,900 to federal law,
whose articles were read from the official Fedlex text when the law was
ingested (level `verified`), and 3,434 to cantonal law, read from the
official PDF of the Schaffhauser Rechtsbuch (level `Gesetze-PDF`); none is
unverified. The level is the cited article's, one column for every surface;
it records where the article text came from at ingest, not a later re-check
against the live text, and no cantonal article carries `verified`. The DVSH
model and the SHEP portal are the sources of truth for service facts and
were read strictly without changing anything.

The verdict files the loaders read (one JSON per Formular from the review
passes) are transient and are not kept in the repository. What they produced
is inspectable in the database itself: `data_field.derived_by`,
`last_checked` on `article` and `data_field_legal_basis`, the `panel_review`
table (2,638 second opinions — 458 of them on the parties of a Formular,
1,162 on the subjekt of a field; 7 still «offen»: 5 items added on
2026-09-26 that await the second review and 2 where the second review
disagreed), `partei_urteil` (the judged parties and data points of each
Formular, with their quotes) and `begriff_vorschlag.herkunft`. The single
corrections that were verified by hand are kept under `quellen/korrekturen/`
and `quellen/rechtsmittel/`, with the script that applies them. One check a
peer can run: every article a field citation points to must carry a
`verified` or `Gesetze-PDF` level —

```sql
SELECT count(*) FROM data_field_legal_basis d JOIN article a ON a.id = d.article_id
WHERE a.last_checked NOT LIKE 'Gesetze-PDF%' AND a.last_checked NOT LIKE 'verified%';
-- 0
```

**Parties.** Stage B2 judged 458 Formulare from their own text. Every party
and every assignment carries a quote that the loader (`rollen.py laden`)
finds again in the Formular text — the PDF text layer, the Word or Excel
content, the DVSH form definition —, and every judgement had a second
review. `panel_review` keeps the latest review per Formular: 382
confirmed, 76 changed — 15 changed by the second review itself and 61 by
the corrections after the audit below (reason «Audit 2026-10-05…»), which
took the place of the earlier entry of those Formulare. An audit of 100 judged data points,
drawn at random with the seed 20261005 in three strata (40 of the
applicant, 30 of another party, 30 «unklar», out of 3,377, 5,968 and
2,315), found 69 of the 70 assignments right and 1 wrong (a telephone
number and an e-mail address in a contact block given to the firm; that
point and the same pattern on five further Formulare are «unklar» now); of
the 30 «unklar», 18 were rightly so, 7 borderline and 5 settled by the
Formular text. Today 73 of the 100 have a party, each with the role the
audit holds right, and 27 are «unklar»: 19 where the audit holds «unklar»
right, the 7 borderline ones and 1 that the Formular text settles but the
field's subjekt still blocks. The audit is kept point by point in
`quellen/parteien_stichprobe_2026-10-05.json`: the 13 points the audit
did not hold right (1 wrong, 5 settled by the text, 7 borderline) carry
their evidence, the other 87 their verdict only. Every build counts it again against today's
parties, and the page «Datenmodell» shows the result; assignments changed
after the audit outside the sample are not part of it.

**eCH corrections of 2026-10-05.** Every data point the register layer
marks — vorbefüllbar, or held by a register — was read again for labels
that ask for another time, another person, a yes/no on an element that
holds a value, or the value of a past event. 24 data points carried an eCH
element that names another Angabe than the label asks for («Zivilrechtlicher
Wohnsitz in der Schweiz seit» mapped to the Zuzug date of a Gemeinde,
«Änderung Zivilstand › Datum» to the departure date, the box «Schüler(in)»
to a postal address); 23 now carry no standard and one the date of the
civil status. Each correction names the old element, the reason, a quote
from the Formular text and its second review
(`quellen/korrekturen/prefill_inhalt_2026-10-05/`, applied by the eCH
loaders). 17 further entries record points that were checked and keep
their element, each with the reason; 11 of them ask for a value of another
time, and the time rule keeps them from the prefill. The register gate of
`validate_db.py` checks on every build that each correction file is
applied as a whole and not overwritten since.

**Law titles of 2026-10-05.** The first ingest had left 36 cantonal law
titles wrong — 19 cut mid-title, 13 with the line «Vom … (Stand …)», 4
with the Rechtsbuch's footnote marker «*» — and 66 short titles: 59 were
the first 40 characters of the title, 2 only «Gesetz», 5 carried the
marker «*» or broke off mid-title. `scripts/load_gesetz_titel.py`
reads the title block of the PDF each law's articles were read from (the
same file and SHA-256 as `gesetz_stand`) and corrects only such names; the

`quellen/korrekturen/gesetz_titel_2026-10-05.json` (70 laws), and
`validate_db.py` refuses a law title with the edition line or the footnote

**Concepts.** The members of the 27 concepts are listed with their reason
in `quellen/konzepte.json`: drawn up from the eCH schemas under `ech_xsd/`

member and every exclusion looked up in the schema of its standard, every
label of its data points read, two searches for missing members, 20
deviations checked against the Formular text). `konzepte.py` counts a
listed element only when it is in the eCH catalogue, has one of the
concept's data types and carries one of the concept's terms of the naming
layer (without a term, the concept's label); a listed element that fails
is shown as «gesperrt» — none today.

**Datenstand.** The dashboard's home page names the date each layer was

The page «Gestaltung der Formulare» names its own date: the Formular files

## The Datentresor

`datentresor.db` shows how the collected data could actually be stored: 1,200
synthetic residents, 10,000 cases, 207,628 stored values, and 2,019 further
uses in later cases that reused an earlier value instead of asking again
(figures from the once-only ledger of the `datentresor.db` built on
2026-10-05 from the parties as stage B1 had settled them, before the
judgement per Formular — see its `meta` table; `./build.sh --tresor`
rebuilds it from the current party layer and prints the new figures).
The rules are enforced by the database itself: the applicant's own datum is
stored once and reused (once-only, by the party layer; a spouse's or a
child's name, a company's or an authority's address is stored per case,
never as the person's). The stored unit is the canonical Angabe, named by its
permanent identifier: the table `angabe` holds the 54 Angaben this vault
reuses, each with its identifier from `citygov.db` (e.g.
`sh:angabe:eCH-0044:firstName:personIdentificationLightType`), and 7,150 stored
values point at one of them; a case names its Formular and service, a
stored value its article, by permanent identifier too. Since 2026-10-04 the vault no longer stores the
running number `canonical_attribute.id`, which the build renumbers whenever
the field layer changes: in the vault of 2026-09-16 (commit 03b7872) read
with the numbers of today, 177 of its 178 numbers point at another eCH
element than the one stored beside the value. Sensitive values
(8,306 in this build) are AES-256-GCM encrypted with the key kept outside the
database, and triggers refuse unencrypted sensitive values, wrong formats,
hard deletes, any change to the access log, and any value that carries neither
an article, nor a consent (given only for proven over-collection), nor an
explicit label — «Aufgabenerfüllung» (needed for the task), «aufgabennotwendig
— Grundlage nach KDSG Art. 5 Abs. 1 noch nicht benannt» (a besonders
schützenswerte Angabe whose Art.-5 basis is still open), «Rechtsgrundlage zu
ermitteln» or «Aufgabenbedarf noch nicht beurteilt». An unresearched basis is
therefore stored as a labelled gap, never as consent: 155,444 values cite an
article, 553 rest on consent, 51,631 carry one of those labels (figures of the
vault built on 2026-10-05). Views answer the standard data-protection
questions directly: `v_auskunft`, `v_loeschliste`, `v_verzeichnis`.

`datentresor.key` is deliberately not in the repository. In the committed
`datentresor.db` the encrypted values therefore appear as `[verschlüsselt]`
in `v_auskunft` and cannot be decrypted. Rebuilding (`./build.sh --tresor`)
creates a fresh key locally and re-encrypts; it needs a Python with the
`cryptography` package (the project uses `.venv/bin/python3`, which
`build.sh` picks up automatically). Without it the build falls back to a
labelled demo cipher and records that in the `meta` table. The file is not
byte-reproducible because the AES-GCM nonces are random, so every rebuild
adds a new copy of about 18.5 MB to the repository history for good. Rebuild
it only when the vault logic or the field layer it samples has changed
materially; the file (62.3 MB, 59.4 MiB) is over GitHub's 50 MiB warning
size, so a push that carries it shows a warning, and GitHub refuses files
over 100 MiB.

All data in `datentresor.db` is synthetic (its `meta` table says so): the
residents are drawn from fixed name lists with a fixed seed. The rest of the
repository holds only what the canton itself publishes: office contact
details from the DVSH model and the SHEP portal (some of them name a staff
member), and the official Formular files exactly as downloaded from sh.ch,
including the metadata the files carry.

## Building

```bash
./build.sh            # every generated surface from citygov.db
./build.sh --tresor   # additionally rebuild datentresor.db
./build.sh --pdf      # additionally write dossiers/*.pdf (local only)
```

One command rebuilds everything in dependency order: `init_register.py`
(rewrites the derived table `canonical_attribute` and the derived column
`data_field.format_code` inside `citygov.db`, refreshes `format_pattern` and
adds any new Dienststelle name to `dienststelle`) → `kennungen.py` (the
permanent identifiers: a new object gets one, a gone one is marked
«entfallen», none is reused; writes nothing when nothing changed) →
`rollen.py ableiten` (the parties of every data point: stage B1, with the
loaded stage-B2 judgements applied over it; says «unverändert» when nothing
changed) — these three are the only steps that write to the database, and
only derived data, each through staging → validate → swap → with
`--tresor`, `build_datentresor.py` (`datentresor.db`, built before the
export reads it for the Bürgersicht) → `export_json.py` (`data_export.json`,
with the comparison of the Gestaltung from `gestaltung_export.py`, the
parties (`rollen.py`), the change-impact index (`wirkung.py`), the register
map and the corrected prefill count with its time rule (`register_map.py`),
the concepts (`konzepte.py`, from the reviewed `quellen/konzepte.json`), the
figures of the pages «Datenmodell» and «Was Register schon wissen» (with the
audit `quellen/parteien_stichprobe_2026-10-05.json` counted again against
today's parties), the permanent identifiers and the version stamp of the
export contract (`export_vertrag.py`), and today's entry in `verlauf.json`;
both are written only after its own gates passed — every figure with parts
sums to its total, every Dienststelle adds up, the parties, the register
figures, the concepts, the figures of the two pages and the change-impact
index add up, every identifier resolves, no layer failed silently —
otherwise it ends with «ABBRUCH … nichts geschrieben») → `theme.py
--check` (the shared look: every text colour reaches 4.5:1 on its
backgrounds, no colour, size or font literal is left in a page generator)
→ `build_flows.py` (`flows.html`; its profile prefill holds only the
applicant's own answers, the rule of `citygov_prefill.json`) →
`export_llm.py` (the `citygov_*` exports; stops when its prefill map and
the dashboard's «vorbefüllbar» disagree, or when a prefilled point belongs,
by `citygov.db`, to anyone but the applicant) → `export_ech_schema.py`
(`citygov_ech_schemas.json`) → `build_dashboard.py` (`dashboard.html`;
after the exports, because the page «Datenmodell» shows the version of
every export as `exportvertrag.json` records it; stops with «ABORT» on an
export that lacks a figure the page reads instead of computing) →
`export_vertrag.py` (read-only: every export carries the version
`exportvertrag.json` records, matches its schema under `schema/` and its
recorded counts) → `kennungen.py --pruefen` (read-only: every object has
exactly one active identifier, and each names its object) →
`export_dossiers.py` (`dossiers/`) → `build_index.py` (`index.html`,
`404.html`) → `validate_db.py` (with the gates of the identifiers, parties,
law editions and registers — the register gate includes the time rule of
the prefill and the eCH correction files of 2026-10-05 and reads
`quellen/register/` —, of the concept file and of the law titles) → `check_pages.mjs`, the
automatic page check. The build reads nothing outside the repository. It prints the sizes of
`dashboard.html`, `flows.html`, `data_export.json` and `citygov_llm.json`,
then the result of the page check, and writes `logs/citation_todo.txt`
(every ingested law article not at level `verified`) locally; `logs/` is not
tracked. A `--pdf` build adds a PDF column to `dossiers/index.html`; run a
plain `./build.sh` before committing, so the published index does not link
PDFs that are not in the repository. A second run on the same data
reproduces every generated page and export byte for byte apart from the
`generated_at` stamp, and leaves `schema/` and `exportvertrag.json` untouched
(no change, no new version and no entry in the list of changes); `citygov.db`
is the exception — `init_register.py`
recreates its derived rows on every run, so the file's bytes change while its
content does not, and `git status` lists it after every build.

**The page check.** The last step, `node scripts/check_pages.mjs`, opens the
built pages in a local headless Chrome (driven through a pipe, without
network) and fails the build with one plain message per finding: an inline
script that does not parse, a page that does not start or writes an error to
the console, a request to another host, a bar or a list whose numbers do not
add up to the total it states, a text colour below 4.5:1, a link in the
browser's default blue, text below 12 px, a `dashboard.html` of 95 MiB or
more (GitHub refuses files over 100 MB; below that, size is no goal), or something clickable that the keyboard cannot reach. It takes about 20
seconds (30 dashboard routes and 6 documents); `--only <check>`, `--verbose` and `--breite <px>` (a window of
another width) narrow or widen it. Without Node or Chrome it prints
«Seitenprüfung übersprungen: Node oder Chrome nicht gefunden» and the build
succeeds; a Chrome that is found but does not start fails the build with the
cause («Seitenprüfung fehlgeschlagen: …» — in a container set
`CHROME_FLAGS=--no-sandbox`; `CHECK_PAGES=skip` builds without the check on
purpose). `scripts/README.md` lists every check and what clears it.

Loading new data is a different job. The loaders under `scripts/`
(`load_*.py`, `ingest_*.py`, `sweep_ech_xsd.py`, `run_begriffe.py`,
`scan_gestaltung.py`, `gesetz_stand.py`, `check_gesetz_stand.py`,
`register_katalog.py`, `register_map.py`, `rollen.py laden`, and the one-off
`migrate_*.py` corrections) each write to a staging copy, validate, and only
then replace the database, so a failed loader step leaves `citygov.db` as it
was before that step. `run_begriffe.py`
is a chain of such steps, each swapped on its own: when a later step fails,
the earlier ones stay applied, so rerun the whole chain. `sweep_ech_xsd.py`
keeps the XSD files it downloaded even when its database write fails.
`scripts/README.md` gives their order, from the law chain to the flows, and
a one-line purpose for every script. No script that needs the network or
`pypdf` is a step of `./build.sh`: `check_gesetz_stand.py` and
`register_katalog.py --abrufen` ask official sources over the network (so
do the older loaders named under «Requirements»);
`scan_documents.py`, `scan_gestaltung.py`, `rollen.py laden` (it finds every
quote of a judged party in the Formular text), `register_map.py
--korrekturen` (it finds every quote of the eCH corrections of 2026-10-05 in
the Formular text) and `fill_pdf.py` read PDF Formulare with pypdf, as do the law loaders
`ingest_bigcode.py`, `extract_quotes.py` and `load_gesetz_titel.py --lesen`
(the title block of each law's PDF; applying the titles needs no pypdf).
Without the network or pypdf, `./build.sh` still runs: it reads what these
loaders stored — `gesetz_stand_pruefung`, the register tables and
`quellen/register/`, `partei_urteil`, the applied correction files. `konzepte.py` is not a loader:
nothing writes `quellen/konzepte.json` but a reviewed edit, and the
database holds no concept table.

**Requirements.** Python 3. `./build.sh` itself needs only the standard
library (`--tresor` encrypts with AES-256-GCM when the `cryptography`
package is installed and otherwise falls back to a labelled demo cipher, see
«The Datentresor»); `--pdf` needs Google Chrome at its macOS location
(`/Applications/Google Chrome.app`). The page check at the end of `./build.sh`
needs Node (16 or newer) and a local Chrome, Chromium or Edge; without them
it is skipped and the build still succeeds. The loaders and harvesters need
`pypdf` and `openpyxl` (`scan_gestaltung.py`, the measurement of the
Gestaltung, refuses to start without pypdf; it was written and tested with
pypdf 6.13; `rollen.py laden`, which checks every quote of a judged party in
the Formular text, `register_map.py --korrekturen` and
`load_gesetz_titel.py --lesen` need it too); the
Datentresor build uses `cryptography` for real encryption —
all three are in `requirements.txt`:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

`build.sh` uses `.venv/bin/python3` when it exists; run the loaders with it
too.

The loaders need two more things that are not in this repository. First,
macOS: they read law PDFs through `scripts/extract_law.py`, which uses
PDFKit via `osascript` (JavaScript for Automation), and Word Formulare
through `textutil`. `build_gesetze_index.py`, `ingest_laws.py`,
`ingest_fed.py`, `load_data_rules.py`, `load_rechtsmittel.py` and
`load_themenkatalog.py` find no text on other systems, so they skip or
reject. Second, the canton's source folders next to the repository:
`../Gesetze/` (the law PDFs, federal ones in `../Gesetze/Bund/`),
`../Verwaltung/` (the Formular files as the offices hold them, read by
`ingest_new.py`) and `../DVSH/` (the saved DVSH harvests). `gesetz_stand.py`
reads the law PDFs too (macOS PDFKit), and `load_gesetz_titel.py --lesen`
reads them with pypdf. Some loaders use the network, with read-only GETs
only: `fetch_rechtsbuch.py` (a cantonal law PDF), `sweep_ech_xsd.py` (the
eCH schemas; not with `--offline`), `check_online.py` (the Formulare on
sh.ch), `init_verfahren.py` (one request for the title of the VRG),
`check_gesetz_stand.py`, which asks the Schaffhauser Rechtsbuch and Fedlex
for the edition in force (one request per law), and
`register_katalog.py --abrufen`, which fetches the official register sources again
(without `--abrufen` it loads from the kept snapshots in `quellen/register/`).

## Known gaps

- **Legal bases.** The 73 Formulare taken from the DVSH model (42 eFormulare
  built from its form definitions and 31 files from its asset store) have
  their standards mapping but not yet their article-level legal bases: 1,098
  fields on 74 Formulare are marked "zu ermitteln" — the 73 DVSH-sourced
  ones entirely (1,088 fields) plus 10 fields of one older form.
- **Cantonal decisions.** Schutzstufen and DSFA decisions are the canton's
  to make and stay empty until then.
- **Legal remedies.** A Verfahren outcome is modelled for 172 of the 473
  Formulare; the other 301 have none yet. Of the 172, 104 carry a quoted
  remedy — 20 from a sectoral provision, 84 the general VRG rule, and 31 of
  those 84 are still the default without a Prüfvermerk confirming that no
  sectoral provision applies. 28 end without an appealable decision, 16 have
  an outcome the DVSH text does not back (so the remedy question is not
  reached), and 24 have none: 18 were assessed and could not be decided from
  the cited law (mostly commercial-register and notarial acts under federal
  law), 6 have not been looked at yet. The dashboard says which is which.
- **Standards.** eSH is a draft and shrinks as eCH assignments take fields
  over. Where the corpus is split on how a datum is demanded, the entry asks
  for a cantonal decision instead of naming an outlier.
- **Naming.** Data asked under a single label are not checked for a common
  term yet; the Begriffe page says how many.
- **Currency.** 312 Formulare are overdue for their online re-check and 64
  have never been checked against sh.ch: 22 Formulare with a file and the 42
  eFormulare, which have no file there to compare (see Datenstand above).
- **One DVSH eFormular not loaded.** Service 640 (Atelierstipendien in
  Berlin, DVSH 206, split off on 2026-09-27) has its own DVSH eFormular
  definition with 15 fields. `scripts/link_dvsh_eforms.py` would add it as
  a 43rd eFormular; it has not been run since the split, so the service is
  counted among those without a Formular.
- **Guided flows** exist for 57 of the 473 Formulare.
- **Parties and roles.** 2,313 of the 11,914 data points have no party
  («unklar», each with its reason), and the 26 roles are a proposal until
  the canton confirms them. 264 of the «unklar» points, on 105 Formulare,
  carry the reason «Subjekt passt nicht»: the party the Formular names has
  another entity type than the field's judged subjekt, so they wait for a
  second review of the subjekt. 4 Formulare without readable text (two
  .doc, one .xls, one scanned PDF) and 2 eFormulare (500, 501) were not
  judged and keep the result of stage B1. The role «betroffene Person» (the
  person a Formular is about where it does not call that person the
  submitter: 707 data points on 44 Formulare) may be the applicant; the
  databank counts its Angaben as another party's.
- **Prefill and parties.** «Vorbefüllbar» (841) counts only the applicant's
  own answers. 1,246 answers with the Einwohnerregister mark belong to
  another party — 442 of them, on 47 Formulare, to family members (spouse,
  child, parent, other relatives, a person in the household; 159 of these
  are required, on 24 Formulare) — and 66 to a party not yet settled. Another person's data can
  come from the register only if the municipalities may deliver relations;
  that is the canton's decision, as is whether an office may fetch from the
  register at all (the figure counts what the applicant's profile would
  fill). Formulare 107 (Choix du système d'assurance-maladie) and 144
  (Meldeformular für GrenzgängerInnen) concern people who may live abroad
  and then are in no Swiss Einwohnerregister; their 12 required answers are
  counted all the same.
- **One element per Angabe and role (Konzepte).** The 84 Vorschläge wait
  for the canton's confirmation and the 263 other cells for its decision
  (in 197 of them, with 632 data points, every data point already uses the
  same element, but the cell has fewer than 10); that a cell is a concept ×
  role × entity type is the databank's choice.
  Whether the concept findings enter the headline figures or the
  Handlungsbedarf is open; today they do not. 488 data points of the
  concepts have no party yet and are in no cell. The layer shows element
  mappings of the field layer that name another Angabe than the label asks
  for and are not corrected yet — among them first names mapped to the
  name in a foreign passport (eCH-0011, 10 data points on 9 Formulare), a
  spouse's or a child's AHV number mapped to the employer's (eCH-0278
  vnEmployer, Formulare 116 and 232) and the names of 8 organisations
  mapped to elements for a person's name.
- **Law editions.** 33 laws that data fields cite (3,008 citations on 193
  Formulare) have a newer edition in force than the one their articles were
  read from; they are listed for re-reading, not re-read — when the
  databank reads them again with the newer edition, and checks each
  citation against the new text, is open. 86 editions are known only from the
  head of the PDF the loaders read, not from a record made when the articles
  were read. For 72 cantonal laws the Rechtsbuch keeps two versions with the
  same Stand, one «formlos berichtigt»; which of the two was read cannot be
  told. 20 laws already have a later edition published that comes into
  force between 2027-01-01 and 2029-01-01, 16 of them cited by data fields;
  no repeal is published (Fedlex also lists announced editions without a
  publication date or text — kept as «angekündigt», never counted). For 4 cited laws whose edition comes
  only from the head of the PDF (SHR 814.201, SR 412.10, SHR 210.100, SHR
  935.901; 147 citations) no cited article has a stored text, so no text
  comparison ties the stored articles to that file; the export marks them
  «Datei nicht mit gelesenen Artikeltexten abgeglichen».
- **Prefill, owner decisions.** Three points stay «vorbefüllbar» until the
  owner decides: Formular 182 «Datum der Ausreise» asks for the planned
  departure, which the register holds only after the Abmeldung; Formular 149
  «Änderung Zivilstand › Datum» is the date of the change being reported,
  while «Zivilstand neu» of the same change is not prefilled; Formular 238
  «Lebensmittelpunkt» is the question the questionnaire is meant to settle.
  The reasons stand in
  `quellen/korrekturen/prefill_inhalt_2026-10-05/teilfelder.json`: 182
  and 238 among the points checked and kept (`geprueft_belassen`; 182
  because its element names the departure date, 238 because the RHG
  describes the Niederlassungsgemeinde by the centre of life), 149 among
  the corrections (its element is now the date of the civil status, which
  the time rule lets through). The optional «Datum Änderung Zivilstand» of
  Formular 146 is prefilled under the same exception as 149.
  The time rule applies to the prefill only: the register figures count the
  element, so the 90 data points with the Einwohnerregister mark that ask
  for a value of another time stay among the Angaben a register holds and
  in the model minutes.
- **Headline figures of 2026-10-05.** Two corrections of that day moved
  figures of the data standard against the published build of 2026-10-04:
  the 24 eCH corrections of the prefill review (8,144 instead of 8,167 data
  points with an eCH element, 3,539 instead of 3,543 named differently,
  3,564 instead of 3,541 without a standard in force) and the subjekt of
  the 57 fields corrected after the party audit, which the comparison of
  «the same Angabe» reads (6,666 instead of 6,701 demanded the same way: 15
  of the 35 through the subjekt, 20 through the eCH corrections); the open
  points moved with them. The trend note of 2026-10-05 names both causes.
  The owner has yet to accept these moves.
- **Registers.** The figures say what a register holds, not that an
  office may fetch it. Access is «offen — rechtlich zu klären» for 15 of the
  18 registers; for the Grundbuch, the Handelsregister and the
  Steuerregister an ingested article is quoted as a candidate (for the
  Steuerregister also a limit), which the canton's lawyers still have to
  assess; § 6 of the Verordnung über das Einwohnerregister (SHR
  431.101), on the cantonal Personendatenplattform, is not ingested. An
  Angabe without an eCH element or eSH key (vehicle plates and Stammnummern
  with «standard without element», for example) is mapped to no register,
  and the mapping inherits every wrong element of the field layer: five
  applicants' «Geschlecht» fields and some fields about horses, wild boars
  and circus animals carry the dog element of eCH-0185 (the dog database
  ignores them, but the field layer should correct them). No fetched source
  names the Führerausweis as a document of the IVZ (IVZ-Personen holds
  «Ausweisdaten» of driving permits), so no Beilage is attributed to it by
  that word; the general animal form «Tiermeldeformular» does not say
  «Hund» and is not counted for the dog database. The
  Steuerregister and the BUR have only the upper bound by standard, because
  no source names their Angaben one by one. Every minute figure is a model
  estimate for one pass through a Formular: case numbers per service are the
  canton's data.
- **Identifiers.** The base address for resolvable identifiers is not
  chosen yet (a canton-owned domain is preferred), and identifiers carry the
  service and Formular slugs as they were on 2026-10-04, ingest artefacts
  included; once published they never change — a cleaner one can only
  supersede them («abgelöst durch», from a reviewed decision file). 131
  further article rows in 59 laws carry a cross-reference or a text
  fragment as their «heading» — it begins with «Abs.», «ff.», «lit.»,
  «Ziff.» or a lower-case word, as in «Abs. 4 bleibt vorbehalten.» or «und
  163» —, 15 of them cited by a data field; whether each is a real article
  with a misread heading or an artefact like the two removed on 2026-10-05
  is not checked yet, and each already has its identifier.
- **Gestaltung der Formulare.** The yardstick is the practice of the
  measured Formulare, not the canton's corporate design, whose manual is not
  in the databank: «entspricht der Praxis» does not mean that a Formular
  meets a rule, nor «weicht ab» that it breaks one. Five Merkmale wait for
  the canton: four show no clear practice, and the databank knows no rule
  on a minimum font size; whether the canton has laid down a rule for any
  of them, the databank does not know. Accessibility is checked only for
  its machine-checkable Mindestmerkmale; reading order, alternative texts,
  contrast and the quality of tags and field descriptions are not checked.
  Nothing inside an image is measured (logos, their colours, text in
  images), and federal Formulare and those of other cantons, foreign
  authorities or third parties are measured like the canton's own. Not
  measurable: the 3 files in an old format, and the text of the 2 scanned
  PDF and of 2 PDF that store their text unreadably. The 42 eFormulare are
  not judged. The measurement is not part of `./build.sh`: after a new
  Formular or a changed file, run `scan_documents.py` and then
  `scan_gestaltung.py`. A Formular without a row — a new one, or one whose
  changed file `scan_documents.py` has registered — is shown as «noch nicht
  gemessen».
- **Retired layer.** The auto-draft layer of 2026-06 (tables `form_field`,
  `field_mapping`, `requirement` and their links) is retired: the curated
  `data_field` layer replaced it, and its field drafts are not exported. The
  tables stay in the database for the record; its 388 per-service notes
  remain in `citygov_llm.json` (`services[].findings`), marked there as
  legacy text.

The Handlungsbedarf board and «Recherche der Databank» together list every
open point by Dienststelle (the CSV export holds all of them); the dashboard
shows each one where it occurs.
